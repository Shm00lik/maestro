# R7-R9: tool restriction, usage accounting, acceptEdits + stdio permissions

## Question
- **R7:** Can a session be made unable to edit files (planner/read-only sessions) with `--permission-mode acceptEdits --disallowedTools "Edit,Write,NotebookEdit"`, or is `--tools <list>` needed?
- **R8:** In one long-lived stream-json process, are `result.usage` / `result.modelUsage` per-turn or cumulative across turns?
- **R9:** With `--permission-mode acceptEdits --permission-prompt-tool stdio`, what happens to a pending `can_use_tool` request when the interrupt `control_request` is sent, and does `acceptEdits` still auto-approve Edit while stdio is on?

## What I ran
claude 2.1.312 (model `claude-haiku-5-5`), Windows 11, `claude.exe` spawned with `shell:false` as in R5, scratch repo `%TEMP%\maestro-spike-repo`, `--model haiku`. Script `spikes/r7-r9/run.ts <r7a|r7b|r8|r9>` (spawn/stdio code copied from the R2/R3 spikes); raw output `spikes/r7-r9/out-*.jsonl` is git-ignored. Before each run the script rewrites `target.txt` to `"alpha\nbeta\ngamma\n"`. Common args: `-p --input-format stream-json --output-format stream-json --verbose --model haiku`. **Four claude invocations, each a single run (nothing repeated):**
1. `r7a`: `+ --permission-mode acceptEdits --disallowedTools Edit,Write,NotebookEdit`. Prompt: `Edit the file target.txt in the current directory: change the line "beta" to "BETA-EDITED". Do it now.`
2. `r7b`: same prompt, `+ --permission-mode acceptEdits --tools Read,Glob,Grep`.
3. `r8`: `+ --permission-mode acceptEdits`; msg 1 `Reply with exactly: one`; msg 2 `Reply with exactly: two`, written on stdin right after the first `result` arrived, same process.
4. `r9`: `+ --permission-mode acceptEdits --permission-prompt-tool stdio`; one prompt: use Edit on target.txt (beta -> BETA-EDITED), then use Bash to run `npm --version`. On the Bash `control_request` I did not answer it; 2 s later I wrote `{"type":"control_request","request_id":"int-1","request":{"subtype":"interrupt"}}`, kept reading 18 s, then ended stdin.

## Observed (verbatim, run-labelled)

### R7 run 1 (`r7a`, `--disallowedTools Edit,Write,NotebookEdit`): the Edit tool was blocked, but the file WAS changed via Bash
`init.tools` listed no `Edit`, `Write` or `NotebookEdit` (it did list `Bash`, `PowerShell`, `Read`, ...). The model still called Edit; what it saw (`tool_result`, `is_error:true`):
```
<tool_use_error>Error: No such tool available: Edit. Edit is disabled for this session, in subagents as well as here.</tool_use_error>
```
It then wrote "The Edit tool is disabled in this session, so I'll make the same single-line change with a shell command", called Bash `sed -i 's/^beta\(\r\?\)$/BETA-EDITED\1/' target.txt && cat -A target.txt`, got a `tool_result` with `is_error:false`, and replied that it changed the line. That Bash call needed no approval (acceptEdits auto-accepts file-modifying shell commands inside the cwd; no prompt tool was configured and none was needed). File afterwards (script check, verbatim):
- before: `"alpha\nbeta\ngamma\n"`
- after:  `"alpha\nBETA-EDITED\ngamma\n"`

So `--disallowedTools Edit,Write,NotebookEdit` removes those tools but does **not** stop file edits.

## Decision for Plan 2
**R7 (read-only / no-edit sessions).** `--disallowedTools Edit,Write,NotebookEdit` is NOT sufficient: the model fell back to Bash `sed`, `acceptEdits` auto-accepted it, and the file changed. For any session that must not modify files the runner passes an explicit allow-list: `--tools Read,Glob,Grep` (read-only built-ins only; never `Bash`, `PowerShell`, `Edit`, `Write`, `NotebookEdit`), together with `--permission-mode acceptEdits`. Edit-capable sessions pass no `--tools`. When the model calls a removed tool it gets `No such tool available: Edit. Edit is disabled for this session...` (`is_error:true`); the runner needs no special handling. Caveat: `--tools` did not remove the user's MCP connector tools (8 Claude Docs tools stayed listed); if a restricted session must have no MCP at all, that needs a further flag (e.g. `--strict-mcp-config`, untested here). The runner should assert after `init` that `init.tools` contains none of `Edit,Write,NotebookEdit,Bash,PowerShell` for restricted sessions.

**R8 (per-turn tokens).** Per-turn tokens = `result.usage` as-is (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`); do NOT diff `usage` across turns. `modelUsage` and `total_cost_usd` are cumulative for the process: per-turn cost = `total_cost_usd[n] - total_cost_usd[n-1]`, or read `model_usage_since_last_result` (per-turn per-model delta). Session total = last `result`'s `modelUsage`/`total_cost_usd`, or the sum of per-turn `usage`. A respawned process (`--resume`) is assumed to restart cumulative counters at 0 (untested), so the runner must keep its own running totals and treat the first `result` of each new process as baseline 0 for `total_cost_usd`/`modelUsage` diffs.

**R9 (pending permission on interrupt).** Spawn with `--permission-mode acceptEdits --permission-prompt-tool stdio` (plus the R2 stream-json args); Edit is still auto-approved, only non-edit tools such as Bash raise `can_use_tool`. On user interrupt the runner writes `{"type":"control_request","request_id":"<unique>","request":{"subtype":"interrupt"}}` and then: (a) on `control_cancel_request` whose `request_id` matches a pending inbox item, mark that item cancelled and remove it from the inbox, and do NOT send a `control_response` for it; (b) expect the interrupt's own `control_response` (`still_queued`), then the rejected `tool_result` and `[Request interrupted by user for tool use]` user events; (c) treat the following `result` (`subtype:"error_during_execution"`, `terminal_reason:"aborted_tools"`, `is_error:true`) as the end of the turn with status "interrupted", not "failed" (`permission_denials` lists the cancelled tool). If the user answers an inbox item after it was cancelled, drop the answer silently. Whether the process accepts another user message afterwards with stdio on is unverified; Task 9/10 must cover it with a test.

## Fallback needed?
- R7: no; `--tools <list>` works (single run). `--disallowedTools` alone is rejected as a read-only mechanism. Open item: MCP tools survive `--tools`.
- R8: no.
- R9: no. Open items: new message after interrupt with stdio on, late response to a cancelled request, concurrent requests.
