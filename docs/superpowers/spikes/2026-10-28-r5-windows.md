# R5: Windows process control

## Question
How does Maestro's session runner start `claude -p` on Windows, stop a turn cleanly, hard-kill it without leaving orphans, and run it inside a long worktree path? (Spec section 15, R5.)

## What I ran
Script: `spikes/r5-windows/run.ts`, run with `npx tsx spikes/r5-windows/run.ts <mode>`. Scratch repo: `%TEMP%\maestro-spike-repo`. Node v25.2.1, claude 2.1.312, Windows 11. **Six claude invocations in total**, all `--model haiku`: sigint (early-finish run), sigint (tool run), taskkill, hardkill, long-path claude, taskkill repeat. Modes:
- `shim`, `spawncmd`: no claude API calls (`--version` only).
- `sigint`, `taskkill`, `hardkill`: spawn `claude.exe -p "Use the Bash tool to run exactly this command: ping -n 60 127.0.0.1 . Then reply done." --allowedTools Bash --output-format stream-json --verbose --model haiku`, wait for the `tool_use` event, sleep 3 s, apply one stop method, wait up to 15 s. The script snapshots the process tree (via `Get-CimInstance Win32_Process`) before and after.
- `longpath [longpaths|nolp] [claude]` with env `WT_LEN=<target path length>`: `git worktree add -b spike-long <path>`, then writes a deep file inside the worktree, then `git status` there, optionally `claude -p "say ok"` with that cwd. `cleanup` removes worktree, branch, directory and unsets the scratch repo's `core.longpaths`.
- Caveat: the child's stdin is closed immediately (`-p` needs none), so SIGINT with stdin open was never tested.
- `earlyfinish` mode exists in the script (original "count to 50" prompt). It was not re-run, to save usage; the excerpt below is from the original run, made when that prompt was still in the script.

## Decision for Plan 2
- **Plan 2's runner has NO verified graceful stop.** SIGINT and `taskkill /T` (no `/F`) both fail; the stdin interrupt is untested until R2. The only verified stop is the hard kill, below.
- **Hard kill (the only verified stop):** `spawnSync('taskkill', ['/PID', String(child.pid), '/T', '/F'])`, then wait for the `exit` event (exit code 1, no `result` event). It killed the whole tree with no orphans. Never use `child.kill()` alone.
- **Design proposal (not a finding):** the runner records its own `interrupted` outcome when it issues the hard kill, since no `result` event arrives. If R2 finds a stdin interrupt, use it first with this hard kill as the timeout fallback.
- **Spawn:** `spawn(exe, args, {shell:false, windowsHide:true, stdio:['pipe','pipe','pipe']})` on the native `claude.exe`. Resolve `exe` in this order: (1) locate `claude.cmd` with `where claude`, read it, and take the path on the line containing `claude.exe`, substituting `%dp0%` with the `.cmd`'s directory (here `%dp0%\node_modules\@anthropic-ai\claude-code\bin\claude.exe`); (2) else `where claude.exe`; (3) else fail with a clear error. Not covered: a native-installer layout that has no npm shim (only `where claude.exe` could find it; not tested). Never spawn `claude.cmd` with `shell:false`. `shell:true` with `claude.cmd` is a possible fallback but is **untested** with stream-json stdio and adds a `cmd.exe` layer plus quoting risk.
- **Worktree paths:** keep them under about 200 characters; check `path.length` before `git worktree add`. 213 worked, 223 failed. Set `core.longpaths` per repo only (not globally) so `git status` can see files deeper than 260 characters inside the worktree. `claude` ran fine in a 198-character cwd.

## Fallback needed?
Yes. Graceful stop has no working method yet: until R2, the hard kill is the only stop. Exe resolution needs the `where claude.exe` fallback and a clear error for unsupported layouts; `shell:true` is an untested last resort. Worktree path length needs a guard and a short-name fallback (for example hashed directory names under a short root).
