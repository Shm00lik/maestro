# R5: Windows process control

## Question
How does Maestro's session runner start `claude -p` on Windows, stop a turn cleanly, hard-kill it without leaving orphans, and run it inside a long worktree path? (Spec section 15, R5.)

## What I ran
Script: `spikes/r5-windows/run.ts`, run with `npx tsx spikes/r5-windows/run.ts <mode>`. The scratch repo was `%TEMP%\maestro-spike-repo`. Node v25.2.1, claude 2.1.312, Windows 11. Five claude invocations in total, all with `--model haiku`.
- `spawncmd`: `spawn()` on `claude.cmd`, the extensionless `claude` shim, `claude.cmd` with `shell:true`, and `claude.exe`. No claude API calls (`--version` only).
- `sigint`, `taskkill`, `hardkill`: spawn `claude.exe -p "Use the Bash tool to run exactly this command: ping -n 60 127.0.0.1 . Then reply done." --allowedTools Bash --output-format stream-json --verbose --model haiku`. The prompt was changed from "count to 50" because haiku emitted all 50 numbers in one message and finished before the stop call (first sigint run). The long-running `ping` gives a real grandchild tree. About 3 s after the `tool_use` event, the script applies one stop method:
  - `child.kill('SIGINT')`
  - `taskkill /PID <pid> /T`
  - `taskkill /PID <pid> /T /F`
- `longpath`: `git worktree add -b spike-long <path>` for worktree paths of 198, 213, 223, 230, 238 and 253 characters, with and without `core.longpaths` set in the scratch repo only. Then `claude -p "say ok"` with cwd set to the 198-character worktree. A `cleanup` mode removes the worktree, branch and directory.

## Observed
**Spawning.**
- `spawn('claude.cmd', ..., {shell:false})` throws `EINVAL`, synchronously.
- `spawn('...\npm\claude', {shell:false})` fails with `ENOENT`, because the extensionless shim is a bash script.
- `claude.cmd` with `shell:true` works, but gives a DEP0190 warning and an extra `cmd.exe` layer.
- `claude.cmd` is only a wrapper. It runs `%dp0%\node_modules\@anthropic-ai\claude-code\bin\claude.exe`. In this install (2.1.312) `claude` is a native exe, not a node script. `spawn(<that claude.exe>, args, {shell:false})` works, with no `cmd.exe` and no node in between.

**PID tree** (`claude.exe`, `shell:false`, mid tool call):
```
claude.exe (spawned pid)
  conhost.exe
  bash.exe -> bash.exe -> (conhost.exe), bash.exe -> PING.EXE
```
One real process, `claude.exe`, plus the tool subprocess tree. No `node.exe`. `where claude` finds only the `.cmd` and the shim. The user also has many unrelated `claude.exe` processes, so any orphan check must use the PID tree, never the name.

**`child.kill('SIGINT')`.**
- On Windows this is `TerminateProcess` on the root only. Exit was `signal=SIGINT` and there was **no `result` event**.
- The bash, bash, bash and `PING.EXE` children were left **orphaned** and kept running. I killed them by hand with `taskkill /PID <orphan> /T /F`.
- A first run, where the turn had already finished when kill was called, returned `kill() === false`, exit code 0 and a normal `result` event (the already-done case).

**`taskkill /PID <pid> /T` (no `/F`).**
- Status 128 and the whole tree survived. Errors: "This process can only be terminated forcefully" for `PING.EXE` and `conhost.exe`, and "One or more child processes ... still running" for the parents.
- The claude turn continued. After 15 s there was no exit (timeout) and the tool call went on.
- Not usable as a graceful stop for these console-less processes.

**`taskkill /PID <pid> /T /F`.**
- Status 0. All 7 processes in the tree were terminated.
- Exit code 1, no `result` event, zero leftover PIDs from the pre-kill snapshot. Clean hard kill, no orphans.

**Graceful stop.** None of the three variants tested ended the turn with a final `result` event. The stdin control-message variant was not tested: **to test in R2** (stream-json input). The `result` event only appeared when the turn finished on its own.

**Long worktree paths.**

| Path length | Without `core.longpaths` | With `core.longpaths` |
|---|---|---|
| 198 | `git worktree add` OK | OK |
| 213 | OK | not tested |
| 223 and up (230, 238, 253) | `fatal: '$GIT_DIR' too big` | same fatal error |

- `git worktree add` hits a git path limit at about 220 characters. `core.longpaths` does not help here.
- `core.longpaths` matters for files **inside** the worktree. A file with a 349-character path was written fine by Node. Without the setting, `git status` printed `warning: could not open directory '...': Filename too long` and skipped the directory. With it, `git status` listed it (`?? dddd.../`).
- `claude.exe -p "say ok"` with cwd set to the 198-character worktree worked: normal `result` event, exit 0.
- Worktree, branch and temp directory were cleaned up. The scratch repo's `core.longpaths` is unset again. Global git config was not touched.

## Decision for Plan 2
- **Spawn:** resolve the native binary from the npm shim: `path.join(<dir of claude.cmd from where claude>, 'node_modules/@anthropic-ai/claude-code/bin/claude.exe')`. Call `spawn(exe, args, {shell:false, windowsHide:true, stdio:['pipe','pipe','pipe']})`. Never spawn `claude.cmd` with `shell:false` (EINVAL). If the layout differs, fall back to `shell:true` with `claude.cmd`, which adds a `cmd.exe` and escaping risk.
- **Stop (soft):** do not rely on `child.kill('SIGINT')` or `taskkill /T` without `/F`. Neither ends the turn cleanly; SIGINT kills the root only and orphans the tool tree. The only candidate for a graceful interrupt is the stdin control message, to be tested in R2. Until then, "stop" means the hard kill below, and the runner records its own `interrupted` outcome.
- **Kill (hard), exact call:** `spawnSync('taskkill', ['/PID', String(child.pid), '/T', '/F'])`, then wait for the `exit` event. It kills the whole tree with no orphans. Treat exit code 1 with no `result` event as a killed run. Never use `child.kill()` alone.
- **Worktree paths:** keep worktree paths under about 200 characters. Check `path.length` before `git worktree add`. Above about 220 it fails with `'$GIT_DIR' too big` even with `core.longpaths`. Set `git config core.longpaths true` per repo for files inside the worktree, never globally. Claude runs fine with a 198-character cwd.

## Fallback needed?
Partly. No graceful stop with a final `result` event was found; only the hard kill works reliably. If R2 finds a stdin interrupt message, use it, with the hard kill as the timeout fallback. For spawning, a fallback is needed only if the npm layout changes (`shell:true` with `claude.cmd`, plus the `taskkill /T /F` tree kill by pid). Worktree path length needs a guard and a short-name fallback (for example hashed directory names under a short root).
