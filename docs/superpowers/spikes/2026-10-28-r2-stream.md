# R2 + R4: stream-json input, interrupts, usage data

## Question
R2: Can Maestro drive one long-lived `claude -p` process over stdin with stream-json (queue a second message mid-turn, interrupt a tool call, resume later), and what are the exact event shapes the Plan 2 parser must handle? R4: does any event carry rate-limit / usage-window data, so Home can show "5-hr usage left"? (Spec section 15.)

## What I ran
Script `spikes/r2-stream/run.ts`, `npx tsx spikes/r2-stream/run.ts <mode>`. Scratch repo `%TEMP%\maestro-spike-repo`, claude 2.1.312 (model reported as `claude-haiku-5-5`), spawned as in R5 (`claude.exe`, `shell:false`). **Four claude invocations**, all with `-p --input-format stream-json --output-format stream-json --verbose --replay-user-messages --model haiku --allowedTools Bash`:
1. `multi`: user msg 1 "List the files here, then wait."; msg 2 "Now count the lines in each file." written as soon as the first `assistant` event arrived; then stdin end.
2. `intctl`: user msg = `ping -n 60` Bash task; after `tool_use` + 3 s, write `{"type":"control_request","request_id":"int-1","request":{"subtype":"interrupt"}}` on stdin; then write another user message on the SAME process.
3. `closestdin`: same ping task; after `tool_use` + 3 s, `child.stdin.end()`; wait 20 s for a `result`, then `taskkill /PID <pid> /T /F` if still alive.
4. `resume`: `--resume <session_id of run 2>` plus a new user message asking what the earlier request was.

Raw output is in `spikes/r2-stream/out-*.jsonl` (git-ignored). No `stream_event` (I did not pass `--include-partial-messages`) and no `api_retry` event occurred in any run, so those two shapes are unverified.

## Decision for Plan 2
**Input shapes** (write one JSON line + `\n` to stdin; the process stays alive between turns):
- user: `{"type":"user","message":{"role":"user","content":"<text>"},"parent_tool_use_id":null}`
- interrupt: `{"type":"control_request","request_id":"<id>","request":{"subtype":"interrupt"}}`
- Spawn args: `-p --input-format stream-json --output-format stream-json --verbose --replay-user-messages [--model …] [--resume <session_id>]`.

**Parser: dispatch on `type`, then `subtype`; tolerate unknown keys and unknown subtypes** (many exist: `hook_started`, `hook_response`, `thinking_tokens`, `task_summary`, `task_started`, `post_turn_summary`, plus `tool_progress`, `rate_limit_event`). Handle:
- `system/init`: `session_id`, `model`, `cwd`, `tools`, `permissionMode`. It can appear again mid-process after an interrupt; treat it as idempotent.
- `assistant`: `message.content[]` blocks of `thinking` (empty text) / `text` / `tool_use{id,name,input}`; `message.usage`; one block per event; `parent_tool_use_id` is non-null for subagent output.
- `user`: string content + `isReplay:true` = echo of a message we sent (use it to confirm delivery); array content with `tool_result{tool_use_id,content,is_error?}` = tool output; array `text` "[Request interrupted by user for tool use]" = interrupt marker.
- `result`: `subtype` (`success` | `error_during_execution`), `is_error`, `session_id`, `stop_reason`, `terminal_reason` (`completed` | `aborted_tools`), `result` (text, success only), `total_cost_usd`, `num_turns`, `duration_ms`, `usage{input_tokens,output_tokens,cache_creation_input_tokens,cache_read_input_tokens}`, `modelUsage{<model>:{inputTokens,outputTokens,cacheReadInputTokens,cacheCreationInputTokens,costUSD,contextWindow,…}}`. A `result` marks the end of a turn, not of the process.
- `control_response`: match on `response.request_id`; `response.subtype` is `success`.
- `rate_limit_event`: see R4 below.
- `api_retry`: NOT observed; model it as optional and unknown-tolerant until seen (do not build logic on a guessed shape).

**Runner semantics:**
1. Follow-ups can be sent at any time; mid-turn messages are queued, injected at the next tool boundary, echoed (`isReplay`), and answered within the SAME turn (one `result`). The runner must not expect one `result` per message. To start a fresh turn, wait for the `result` first.
2. **Graceful interrupt = the stdin `control_request`.** It yields `control_response success`, then a `result` with `subtype:"error_during_execution"`, `terminal_reason:"aborted_tools"` within about 0.1 s, kills the tool's process tree itself, and keeps the process usable for the next user message. Map that `result` to the `interrupted` outcome. Use `taskkill /PID <pid> /T /F` (R5) only as a timeout fallback (suggest about 5 s after the interrupt with no `result`).
3. Closing stdin is not a stop; do not use it to interrupt. Close stdin only when idle (after a `result`) to end the process cleanly (exit 0).
4. Resume: spawn a new process with `--resume <session_id>`; context is retained and the same `session_id` is reused. Persist `session_id` from `system/init`.

**R4 / Home:** v1 CAN show "5-hr usage left" from `rate_limit_event.rate_limit_info.unifiedWindows.five_hour`: left = `(1 - utilization) * 100` percent (if utilization is indeed a 0..1 fraction), reset at `resetsAt`; the 7-day figure is `seven_day`. The event only arrives while a session runs a turn, so Home must show the last seen value with its age (store it with a timestamp), and fall back to "tokens today" (sum of `result.usage` / `modelUsage`) when no event has been seen or the field is missing. The field is undocumented and one account state was sampled, so parse defensively and keep "tokens today" as the always-available secondary figure.

## Fallback needed?
Partly. (a) Interrupt: no fallback in the normal path; keep the R5 hard kill as the timeout fallback. (b) Usage: keep "tokens today" as the fallback display when `rate_limit_event` has not been seen or fails to parse. (c) Unverified, so the parser must tolerate them: `api_retry`, `stream_event` (needs `--include-partial-messages`), `rate_limit_event` under API-key auth, and interrupt behaviour when no tool is running.
